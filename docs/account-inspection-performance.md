# 巡检存储性能优化（2026-10-17）

## 已实施

- `get_account()` 按 SQLite 主键读取目标账号，不再加载和反序列化全部账号。
- 查活/套餐的领取、执行中标记、结果保存共 6 个热路径，改为目标行增量更新；不再删除、重插整个账号表。
- `BEGIN IMMEDIATE` 事务覆盖目标行读取、所有权/快照校验及写回；写入异常回滚。无状态变化时不执行 UPDATE。
- 保留 SQL 列与 JSON payload、`copy_line` 的一致性；保留旧 API 同时传 ID/邮箱时的匹配顺序。

## 本轮没有改变

- 巡检线程数、账号防重、归档快照、同会话自动查套餐、共享套餐限流。
- 逐阶段统计持久化、终态保护与重启标记 interrupted，不用缓冲统计换取速度。
- 没有引入账号快照缓存，账号删除、换绑和 AT 更新仍由当前数据库状态验证。
- 没有重构其他业务的集合全量写入；不能将本轮事务改造等同于全项目支持多实例同时编辑账号。

## 本机前后对比

## 追加：ID 清单与异常停止专项检查

### 已确认并修复

1. **统计更新重复携带完整 ID 清单。** 原先每个账号的统计写回都序列化整个 `account_ids`，一轮任务存在随账号数近似二次增长的清单处理量；历史 API 虽不返回 ID，却仍读取并解析这些清单。现将不可变清单独立保存在 `account_inspection_snapshots`，任务摘要只保存状态和计数。清单和新任务在同一事务中创建；既有记录启动时一次迁移，迁移失败回滚并关闭连接，之后可重试。统计仍逐阶段持久化，没有扩大统计缓冲窗口。
2. **线程故障后其他线程继续领取。** 一个巡检 worker 因数据库读取/统计保存故障退出时，其他 worker 原先可能继续处理剩余清单。现通过共享停止事件停止后续领取；已经领取的账号允许完成当前处理及资源收尾，任务记录失败或中断。
3. 巡检表和索引创建移到数据库初始化，不在每次统计保存、历史读取时重复执行 DDL。

### 大清单验证（本机临时 SQLite，无网络）

| 清单账号数 | 连续 100 次统计写入 | 单份统计 JSON 字符数 |
|---|---:|---:|
| 1000 | 0.248 秒 | 313 |
| 10000 | 0.242 秒 | 314 |
| 100000 | 0.240 秒 | 315 |

该验证检查统计写入成本不随 ID 清单大小放大，不等于执行了 10 万次真实查活。ID 清单本身仍在启动时一次性加载，空间为 O(N)，且历史快照仍占用磁盘；没有声称无限规模或引入磁盘分页调度。

### 仍然存在的性能边界

- 全部 ID 一次性加载及防御性去重有 O(N) 内存成本，适合当前清单调度模型；超大规模需要另行采用持久化分页领取。
- 统计采用同步持久化，SQLite 写入仍串行；这是保留故障恢复统计的当前取舍。
- 登录、取验证码和共享套餐限流仍会决定失效账号的总耗时，不能用本地扫描基准估算实际网络链路速度。

## 追加：单行改造后的邮箱入口复查

固定范围：单行读取/事务写回、Unicode 邮箱兼容、日志轮询入口、清单迁移和并发停止路径。

### 确认的问题及修复

- `get_account_by_email()` 仍使用集合读取；登录前查账号及查活日志轮询会加载全部 payload。改为在 SQLite 中筛选，仅将命中的一份 payload 解码返回，不再在 Python 中加载全部账号详情。
- 上轮 `_select_account()` 使用 SQLite `LOWER(email)`，该函数只处理 ASCII，与历史 Python `str.lower()` 不兼容。例如 `Élodie` 或 Kelvin 符号 `K` 可能匹配失败或选错首个账号。连接注册查询专用 `account_email_lower()`，恢复原有匹配语义；不覆盖 SQLite 内置函数、不改变现有索引定义。按主键读取的热路径不受该函数影响。
- 保留重复邮箱按 ID 首行匹配、空邮箱和不自动去除输入空格的旧行为。

两项问题已先由回归测试复现，再完成修复。新增 3 项回归覆盖禁止集合读取、Unicode/ASCII 混合邮箱匹配及重复/空邮箱兼容。

### 性能与范围

本机临时 SQLite，1000 个账号、每个账号带 2000 字符备注，连续 100 次查找最后一个账号：旧集合路径 2.223 秒，新路径 0.476 秒，约 4.7 倍；无网络。邮箱匹配为了保持 Unicode 语义，仍可能扫描邮箱列（O(N)），并非全部变为索引查询；主要收益是不再加载和反序列化所有账号 payload。主键读取保持索引查询。

本轮没有改动调度方式、限流、统计持久化、清单迁移或进程锁。第二遍复审未发现这些既有路径新的阻塞缺陷；既有的一次性 ID 内存成本、同步统计写入、其他业务集合写入及真实网络 mock 的边界继续适用。

本轮最终验证：全量 **381 项通过**（34.113 秒）；巡检专项 **64 项连续 3 轮通过**（6.736 / 11.252 / 7.967 秒）；Node UI、compileall、`git diff --check` 通过。日志：`/tmp/inspection-email-repro.log`（修前复现）、`/tmp/inspection-audit-full-final.log`、`/tmp/inspection-audit-repeat-{1,2,3}.log`。

## 2026-10-18：锁竞争与初始化资源复查

本轮范围：并发防重、线程故障回收、单行账号写入、快照迁移、UI 请求状态，以及频繁历史轮询的数据库行为。

### 修前复现与修复

1. **空闲历史查询争抢写锁。** `recover_interrupted_account_inspections()` 无论是否存在未完成任务，都执行 `BEGIN IMMEDIATE`。在另一个连接持有无关写事务时，空闲历史轮询会等待，甚至报 `database is locked`。新增回归以真实 SQLite 连接持有写锁，将被测连接的 busy timeout 设为 50ms，修前稳定失败。修复为先只读判断，无待恢复任务直接返回；存在任务时再获取写锁并重新读取，以保证恢复写回使用锁内状态。
2. **连接配置失败未关闭连接。** `_sqlite_conn()` 的函数注册或 PRAGMA 设置异常时，调用方尚未获得连接，无从清理。新增异常路径显式关闭连接，保留原始异常。
3. **数据库初始化的早期失败未关闭连接。** 此前仅快照迁移末段受清理保护，建表/建索引及其他初始化阶段异常仍可能依赖垃圾回收。初始化主体现由连接关闭与事务上下文共同包裹；故障时回滚未提交操作并关闭连接，只有上下文成功退出后设置 READY。没有承诺 DDL 和此前已提交的旧数据导入能够整段回滚。

3 项新增回归均先失败再修复；日志为 `/tmp/inspection-resource-repro.log` 和 `/tmp/inspection-resource-fixed.log`。
